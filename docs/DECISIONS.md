## D1: Application protocol on TCP 8080
- **Source:** ARCH §2.1 and §5.3 (OPEN DECISION), ARCH §17 D1, review item 1.
- **Problem:** the backend HTTP API and the TCP control plane share port 8080. Two listeners on one address and port are impossible. Mixing HTTP bytes and arbitrary binary bytes on one stream without framing is unsafe.
- **Options:**
  1. **Hand-written HTTP/1.1 over raw `SOCK_STREAM`**, with control operations as HTTP endpoints.
  2. A custom framed binary TCP protocol. This needs a different port or an explicitly designed multiplexer.
- **Decision (PROVISIONAL):** option 1.
  - **One** listener: `src/server/backend/control_server.py`.
  - The native Python TCP client (`src/client/tcp/tcp_client.py`) speaks the **same** HTTP/1.1 through `src/common/http/client.py`.
  - None of the available design documents gives a reason to prefer binary.
- **Implications:**
  - One shared HTTP layer in `src/common/http/` is reused by the dashboard (3000), the control plane (8080), the client UI (3000) and the control client.
  - Rubric Step 2 (handshake + ACK) is an explicit application-level request/response, distinct from the OS 3-way handshake.
  - The parser must handle partial reads and writes, header and body caps, and timeouts (see `src/common/http/parser.py`).
- **Not decided yet:** endpoint paths, methods and JSON bodies. These come in Phase 3, in `PROTOCOL_OVERVIEW.md`.

## D2: Server → client event delivery (presence; client-UI events)
- **Source:** ARCH §5.3 and §17 D2.
- **Problem:** HTTP request/response does not push. Two pushes are needed:
  - presence and user list, server → client process;
  - messages, receipts and progress, client process → browser.
- **Options:**
  - polling;
  - long-polling;
  - hand-written Server-Sent Events (an HTTP response stream).

  **WebSockets are prohibited** (PDF §8).
- **Status:** OPEN.
- **Constraint for any option:** a held-open response must not block the listener's accept loop, and event buffers must be bounded (`src/client/frontend/event_hub.py`).

## D3: Reliability semantics across the centralized relay
- **Source:** ARCH §6.4, §12.2 and §17 D4; review item 5.
- **Model:** **two hops**.
  - B↔A and A↔C are separate transport connections.
  - Each connection has two directions, and each direction has its own reliability buffers, RTT/RTO, flow-control window, congestion controller, pacer and send queue (`src/transport/connection_state.py`).
- **Three different confirmations:**

  | Confirmation | Generated by | Proves |
  |---|---|---|
  | Hop-by-hop transport ACK | A (for B→A) | A received the frame. **Nothing about C.** |
  | End-to-end message delivery receipt | C, relayed by A | C's client process received the message |
  | End-to-end file completion (`FILE_DONE`) | C after reassembly **and SHA-256 match**, relayed by A | The whole file arrived intact |

- **Rule:** an ACK from A must never be shown as "delivered" or "file complete".
- **Backpressure:** A's relay queues are bounded per destination. If A→C is blocked, A shrinks the credit it advertises on B→A.
- **Status:** PROPOSED. It is consistent with ARCH's recommendation and needs team confirmation.

## D5: Pacing-rate formula
- **Source:** ARCH §9.7.
- **Options:**
  - `pacing_rate = pacing_gain × BtlBw`, with gain 1.0 (`congestioncontrol.docx`, summary-sourced);
  - `2.0 × cwnd / srtt` in slow start and `1.2 × cwnd / srtt` in congestion avoidance (detailed design).
- **Existing code:** implements the **second** option, using `srtt` with a 0.333 s default before the first sample.
- **Note:** no bandwidth (`BtlBw`) estimator exists. A fake `BtlBw` must not be introduced.
- **Status:** CONFLICT.

## D9: Payload encryption (rubric Step 8)
- **Source:** PDF §4, §6 and rubric Step 8 ("using a standard cryptographic library").
- **Problems:**
  - The Python standard library has **no AES**.
  - `ssl` (TLS) covers TCP only. There is no DTLS for UDP in the standard library.
- **Options:**
  1. Third-party `cryptography` (AES-GCM).
  2. `ssl` for the control plane plus a third-party library for UDP payloads.
- **Status:** OPEN. Not installed and not imported. The constraint scanner flags `cryptography` and `Crypto` until this is approved. It needs team approval, and it is recommended to confirm with the instructor that a third-party library counts as "standard".
- **Packet-format impact:** leave room for a nonce and authentication tag (D14).

## D11: Concurrency model and TimerHost
- **Source:** PDF §6 and rubric Step 4 allow "Multi-threading or Async I/O". The team chose threading and excludes `asyncio`.
- **Problem:** the existing `PacedSender` expects an event-loop-shaped timer host. It is also not thread-safe: `_running` is a re-entrancy flag, not a lock.
- **Design (PROPOSED; skeleton in `src/transport/timer_host.py`):**
  - `ThreadTimerHost` provides `time()` (monotonic), `call_at(when, cb) → handle.cancel()` and `post(cb)`.
  - One scheduler thread per process runs a heap guarded by a `Condition`. The lock is released before callbacks run, and `when <= now` means "next turn", never inline.
  - All transport state is **confined** to that scheduler thread. Other threads use `post()` to reach it.
  - Result: `PacedSender` integrates unchanged.
- **Other threads:** one accept thread per HTTP listener with a bounded worker pool, one UDP receive thread, and one TCP control-client thread.

## D14: Transport sequence model, packets vs frames
- **Source:** ARCH §7.2–7.5 and §8 (summary-sourced); the PDF's references to QUIC and head-of-line-blocking (HoL) elimination; review item 2.

| Aspect | Model A: frame sequence | Model B: packet number + stream offset |
|---|---|---|
| Identity | `seq` per DATA frame (4 B) | New packet number per transmission |
| Retransmission | **Reuses** the same `seq` | Gets a **new** packet number; data identified by (stream, offset) |
| ACK | Cumulative `ack` (LFR) + ≤ 4 SACK ranges | ACK ranges over packet numbers |
| Window bookkeeping | LAR/LFS, LFR/LAF in frames; ring buffer `seq % MaxSlotBuff` | Bytes in flight; per-stream offsets and credit |
| RTT sampling | Karn's rule needed (ambiguous retransmits) | Unambiguous |
| HoL blocking | One sequence space: chat waits behind lost file data | Independent streams avoid it (PDF §7) |
| Fit with existing CUBIC | **Breaks** its assumptions (`pn` never reused; recovery boundary `pn <= recovery_pn`) | Matches |

- **Gated until this is decided:** header fields and sizes, numeric frame codes, ACK/SACK structure, serialization, and the signatures of `reliability.py`, `flow_control.py` and `connection_state.py`.
- Application message types, control operations and transport frame kinds are already separate enums with **no wire values**.
- **Status:** OPEN. **Blocks Phases 4–6.**
